- FCMI (EC XRAM 0x432): 写 0x80/0x81/0x82/0x83 切换性能模式

- WMI设备 AMW0 (UID "IP3WMIEVENT") 提供事件通知

## 四、EC固件风扇控制机制（逆向8051代码）

### 风扇曲线表在ROM中的位置
| 区域 | ROM偏移 | 说明 |
|------|---------|------|
| Fan1表 | **0x2ECB - 0x2F25** | CPU侧风扇 |
| Fan2表 | **0x2F25 - 0x2F7F** | GPU侧风扇 |

### 表结构（每个风扇块 0x5A 字节）
```
+0x00 T1[15]  降温阈值（低于此温度降一级）
+0x0F (1字节间隔, 值54, 勿动)
+0x10 T2[14]  升温阈值（等级0-7的8个值 + 6×FF, FF=封顶不可达）
+0x1E PWM[15] 各等级PWM占空比 (0-255)
+0x2D RPM[15] 各等级目标转速 (×100 RPM)
+0x3C E[15]   降级防抖周期数
+0x4B F[15]   升级防抖周期数
```
（等级0-8为活跃区，索引9-14为备用填充）

### 原厂风扇曲线（解码结果）

**Fan 1 (CPU侧):**
| 等级 | 升温阈值 | 降温阈值 | PWM | 占空比 | 目标转速 |
|------|---------|---------|-----|--------|---------|
| 0 | ≥55°C | — | 47 | 18.4% | 1700 |
| 1 | ≥60°C | <53°C | 75 | 29.4% | 2700 |
| 2 | ≥66°C | <58°C | 86 | 33.7% | 3100 |
| 3 | ≥72°C | <63°C | 97 | 38.0% | 3400 |
| 4 | ≥78°C | <69°C | 111 | 43.5% | 3800 |
| 5 | ≥84°C | <75°C | 127 | 49.8% | 4200 |
| 6 | ≥95°C | <81°C | 140 | 54.9% | 4500 |
| 7 | ≥99°C | <92°C | 153 | 60.0% | 4800 |
| 8 | 封顶 | <97°C | 173 | **67.8%** | 5300 |

**Fan 2 (GPU侧):**
| 等级 | PWM | 占空比 | 目标转速 |
|------|-----|--------|---------|
| 0-8 | 39→162 | 15.3%→**63.5%** | 1400→5000 |

⚠️ **关键发现：原厂曲线最高只有 67.8%/63.5% 占空比！** 这就是满载99-100°C还压不住温度的原因（与无界14X社区发现一致）。

### 控制逻辑（EC代码 @ ROM 0xAE0A / 0xB09C）
- 每tick读取CPU温度（XRAM 0x9600），与T2[level]/T1[level]比较
- 温度≥T2连续F个周期 → level+1（上限8）
- 温度<T1连续E个周期 → level-1（下限0）
- 等级变化时输出PWM[level]，渐变斜坡（+10/+5/+1步进，**上限184**）
- 温度传感器错误(255°C)时按升温处理

### 硬件边界（实测确认，安全关键!）
- **PWM有效范围: 0-184**。**超过184风扇直接停转**（实测PWM 200/220/240/255全部RPM=0）
- EC固件自身的斜坡钳位(0xB8=184)正是这个硬件边界
- RPM响应全程线性: PWM 40→1727rpm, 184→5719rpm (≈27.7 RPM/单位)
- **5720rpm即物理散热上限**（原厂表顶173=5500rpm, 差4%）
- 双风扇同型号（各PWM点RPM差<1%）
- 原厂满载"压不住温度"的根源是散热模组到顶，不是软件封顶

### PWM寄存器层验证（0x1800-0x1821三态dump, 最终确证）
```
0x1801 = 0xB8   PWM周期寄存器(F1通道组) — duty满刻度=184
0x1803 = 0xB8   PWM周期寄存器(F2通道组)
0x1804/0x1809   双风扇duty寄存器, 随写入变化
```
- **duty 184/184 = 100%占空比 = 电气真·全速**, 5720rpm为风扇PWM接口物理极限
- duty>184停转原理: 比较值超过计数器周期值→输出恒断→风扇断电
- 结论: 曲线顶点184配置正确, 无隐藏超速档; 4线PWM风扇100%占空比即额定极速

### EC XRAM 风扇控制寄存器完整映射
| XRAM地址 | Fan1 | Fan2 | 说明 |

## 五、主机访问EC的通道

### 1. ACPI EC RAM窗口（仅XRAM 0x0400-0x04FF，256字节）
- 端口 0x62/0x66 或 MMIO 0xFE0B0400
- 包含：FCMO/FCMI(0x431/0x432), CPUT(0x470), 版本(0x4B0)等
- **风扇控制寄存器(0x0210区)不在窗口内！**

### 2. ITE I2EC协议（可访问全部EC XRAM！）★
通过PNPCFG端口（0x4E/0x4F或0x2E/0x2F，参考同代无界16Pro/14X用0x4E/0x4F）：
```
写寄存器reg值为val:
  outb(0x2e, port); outb(reg, port+1);   # 选择I2EC寄存器
  outb(0x2f, port); outb(val, port+1);   # 写入数据
I2EC寄存器: 0x10=地址低字节, 0x11=地址高字节, 0x12=数据
```

## 六、修改风扇曲线的方案对比

### 方案A：运行时手动PWM（推荐先试，零风险可逆）
```
写 XRAM 0x021F = 0xDC   # Fan1手动模式
写 XRAM 0x021E = PWM值  # 0-255，例如 220 = 86%
写 XRAM 0x029F = 0xDC   # Fan2手动模式
写 XRAM 0x029E = PWM值
恢复：写 0x021F = 0, 0x029F = 0（或重启）
```
优点：立即可逆，无需刷固件
缺点：开机/睡眠后需重设（可做成systemd服务）

### 方案B：修改ROM中的风扇表并刷写（永久生效）
- 修改 ROM 0x2ECB-0x2F7F 的表数据（PWM值/温度阈值）
- 用编程器（如T48+，芯片为XM25RU256C）刷写整片，或尝试AFU
- ⚠️ 风险：刷坏需编程器救砖；EC区与BIOS同片，注意保留其他区域
- 推荐修改示例：把Fan1 PWM表 [47,75,86,97,111,127,140,153,173] 
  改为 [40,70,90,110,140,165,190,215,235] 拉高散热

### 方案C：修改BIOS CBS选项（需要解锁隐藏菜单）
- 改AmdSetupPHX变量：Fan Control=Manual, Fan Table Control=Manual + 自定义温控表
- 需要SCEWIN/SCET工具或解锁CBS菜单后直接在BIOS设置
- ⚠️ 此路径走AMD SMU，本机EC可能不理会，效果存疑

## 八、Fn功能键问题分析（第二阶段）

### 结论：Fn锁功能EC固件已实现，只是没有被任何软件打开！

**机制（逆向EC V2.12键盘翻译代码 @ ROM 0x8DFE）：**
```
按键扫描码 → XRAM[0x0FB5]状态机 → 查翻译表 → 发送PS/2码
                │
                ├─ FNLK==0 或 OSFG==0 → 表A(0x39F0): F1-F12发标准键码(05,06,04...)
                └─ FNLK≠0 且 OSFG≠0 → 表B(0x3A62): F1-F12发媒体键码(86,D4,D5...)
                                          ↑ 这就是按住Fn时的那套键码!
```

**两个开关：**
| 寄存器 | MMIO地址 | 含义 |
|--------|---------|------|
| FNLK | 0xFE0B041A | Fn锁: 0=需按Fn, 1=直接媒体键 |
| OSFG | 0xFE0B0404 | OS就绪标志(需≠0), EC在OS启动后设置 |

**持久化机制（ROM 0xC412的同步逻辑）：**
- XRAM 0x0800-0x080C是"IP3\0"+版本8的持久化配置块
- 其中0x080C=FNLK, 0x080B=FCMO(性能模式), 0x080A=TPTL
- EC周期性检查: 运行值(0x41A等) ≠ 持久值(0x80C等)时 → **自动写入flash保存**!
- 所以主机写一次FNLK=1 → 重启后依然生效

**为什么现在用不了：** DSDT定义了FNLK字段但没有任何ACPI方法/WMI使用它；
EC固件本身也没有Fn+Esc切换热键 → 只有OEM的Windows控制中心能设置 → Linux下无人设置

### 解决方法
```bash
sudo python3 ec_power_fn.py fnlock on    # 一次开启, 永久生效!
sudo python3 ec_power_fn.py fnlock off   # 关闭
```

## 九、充电限制(电池保护模式)分析

### 结论：EC固件V2.12未实现可配置充电限制！

**证据：**
1. DSDT定义了BCTH/BCTL充电阈值字段(EC RAM偏移0x94/0x95)——**但EC固件中对XRAM 0x494/0x495的引用为0处**，纯摆设
2. BIOS Setup中也无相关选项(全部IFR已扫描)
3. AMD PBS设置里的"AC/DC_Better_Battery_Limit"是功耗墙参数，不是充电限制

**但EC内部存在硬编码的"80%电池维护"逻辑（ROM 0x10B1E状态机）：**
- 触发条件: LIDF(XRAM 0x451)复合标志 + 7天计时器(XRAM 0x05C2, 阈值604800秒)
- 行为: 充到80%停止("Switch Bat 80%"调试串), 低于60%恢复充电(SUBB #0x3C判断)
- 充电开关: XRAM 0x0581 bit5(置1=停充, 清0=恢复)——由内部状态机控制, 不在ACPI窗口内
- 这是给"合盖长期插电存放"场景用的自动功能, 没有用户接口

### 可行的变通方案
~~1. **实验性**: 通过I2EC写XRAM 0x0581 bit5手动停充/恢复~~ **(已实验证伪, 见下方实验记录)**
2. **PD适配器功耗问题**: EC通过USB-C PD协商供电("PD Adapter %dmV %dmA"调试串), 满载时100W适配器不够用导致掉电是正常现象, EC固件层面无解
3. EC固件注入补丁(需编程器) — 唯一的"真"充电限制路径, 但存在未解问题(见下)

### 运行时路线实验记录(全部证伪)

| # | 实验 | 结果 | 结论 |
|---|------|------|------|
| 1 | I2EC直接写0x0581 bit5=1(停充) | 1.5秒内被EC回写为0 | 0x0581被EC周期性刷新, 不是主机可写的锁存器 |
| 2 | 写LIDF(0x451) bit1=1(武装80%模式) | 2秒内被清除 | LIDF低3位被定点清除 |
| 3 | LIDF写0xFF观察位存活 | →0xF8: **bit0-2被清, bit3-7存活** | 清除是定点的(只管状态机位) |
| 4 | 7天计时器(0x5C2-0x5C5)写0xFFFFFFFF | 3秒后被复位为1 | 计时器被周期重置(每次bit2重武装都清零→7天永远攒不满, 这可能就是该功能从未生效的原因) |
| 5 | 电池满计数器0x60C | =1(入口条件其实满足) | — |
| 6 | hold80: 8Hz压制LIDF bit1 18秒 | bit在场95%时间, EC零反应 | 80%决策代码不被周期执行 |
| 7 | hold80+: 7Hz压制 LIDF=0x06+计时器到期值, **10分钟** | LIDF在场, chg/BAST/LIDF全程无EC动作痕迹 | **彻底证伪: "Switch Bat 80%"是死代码, 从不在运行路径上被调用** |

**最终结论:** 这套EC固件(V2.12)的充电控制对主机完全不可达。
"80%存储模式"与BCTH/BCTL一样属于**未接线的残留功能**——
状态机代码存在、入口条件(0x60C=1)甚至已满足, 但调用链断路,
且7天计时器被自身逻辑反复重置, 即使调用链通了也永远到不了阈值。

### 固件补丁路线的已知风险
- 停充函数(ROM 0x116B1/0x11686)本身可能也是死代码的一部分——0x581 bit5是否真的控制充电硬件**从未被任何运行证据验证过**
- 若bit5只是状态镜像而非控制位, 注入调用也不会停充, 需要继续逆向真正的充电使能(GPIO或PD控制器命令)
- 需要8051汇编注入+代码洞+编程器刷写(XM25RU256C), 变砖需编程器恢复
